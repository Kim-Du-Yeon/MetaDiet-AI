# 식사 기록 변경과 화면 동기화 (2026-10-19)

## 문제와 원인

검증용 기록을 삭제하면 캘린더 집계는 바뀌지만 상단은 이전 값을 유지했다. CalendarView의 변경 성공 경로에 App의 공유 집계를 갱신하는 연결이 없었다. 대화의 저장 요약은 당시 문자열이어서 삭제 후에도 현재 기록처럼 보였다.

## 변경

- 삭제·분량 수정 성공 후 서버의 오늘 집계를 다시 읽어 상단에 반영한다. 과거 날짜 수정에도 상단은 항상 서비스 시간대의 오늘을 표시한다.
- 요청 실패를 성공으로 처리하지 않는다. 집계 재조회 실패는 기록 변경 실패와 구분하고 재조회 버튼을 제공한다. 응답이 늦게 와도 다른 로그인 사용자의 상태를 덮어쓰지 않는다.
- 대화 복원 시 현재 사용자·대화의 확정 intake proposal 결과에 있는 meal ID를 현재 기록과 대조한다. 삭제·일부 삭제·수정을 구분하고 원래 요약에는 ‘저장 당시 내역’이라고 표시한다. 원본 대화는 변경하지 않는다.
- 기존 영양값을 분량 비율로 환산한다. 캘린더 수정에서 모델이 새 영양값을 만드는 경로를 제거했다. 0·음수·비정상 분량, 기존 영양값 부재는 거부한다. 소유권 검증을 유지한다.
- 새 마이그레이션이나 의존성을 추가하지 않았다.

## 검증

- 백엔드 전체: 1,442 passed, 기존 skip 1건 유지, 기존 deprecation warning 3건.
- 프론트 최종 전체: 118 passed / 33 suites.
- 프로덕션 빌드 성공(빌드 시 ESLint 포함).
- 삭제/일부 삭제/수정/변경 없음, 소유권, 조회 실패 시 삭제 오판 방지, HTTP 오류, 캘린더→상단→대화 갱신을 합성 회귀 테스트로 확인했다.
- 속도·정확도 비교 실험은 수행하지 않았다. 위 테스트는 기능 검증이며 실사용 성공률이나 성능 개선 수치가 아니다.

## 제한

기록 ID가 남아 있는 최근 100개 확정 proposal과 정확히 일치하는 저장 요약만 상태를 연결한다. ID가 없는 레거시 요약이나 그 범위를 벗어난 요약은 삭제 상태를 추정하지 않는다. 동일한 요약이 여러 건이고 상태가 다르면 캘린더 확인 안내를 제공한다. 별도 기기에서 생긴 변경은 대화 복원/새로고침 시 반영되며 실시간 구독은 아니다. 분량 수정은 기존 추정값을 비례 환산하므로 원래 음식 선택의 정확도까지 개선하지 않는다.

### 왜 서버 응답을 기다리는가

현재 경로는 `변경 요청 → 서버 쓰기 성공 → 캘린더 일/월 재조회(병렬) → 세션 복원 재조회 → App 상단·대화 상태 갱신`이다. 세션 복원은 인증을 거쳐 체크포인트·최근 대화·확정 기록 상태와 오늘 집계를 읽는다. 따라서 네트워크 왕복과 DB 읽기 비용이 있으며, 캘린더가 먼저 바뀌고 상단이 뒤이어 바뀌는 짧은 구간도 가능하다. 각 응답은 별도 조회이므로 모든 화면이 하나의 원자적 스냅샷을 공유한다고 보장하지 않는다.

분량 수정은 서버의 기존 영양값 비례 계산이며 이 경로에 영양값 생성을 위한 모델 호출은 없다. 이 갱신 대기를 ‘Agent가 추론하는 시간’으로 설명하면 부정확하다. 무료 서버 기동은 추가 지연 가능 요인이지만 이번 갱신의 주된 지연 원인이나 비중은 단계별로 측정하지 않았다.

서버가 확정한 값을 다시 읽으면 클라이언트가 잘못 차감하거나 쓰기 실패·중복 처리를 놓쳐 집계를 확정하는 문제를 피하는 데 도움이 된다. 대신 후속 조회가 늘어난다. 현재 방식이 유일하게 안전한 방식은 아니며, 서버 변경 응답에 집계와 버전을 포함하거나 낙관적 갱신 후 실패 복구·서버 재검증을 구현하는 대안도 있다.

### 왜 다른 기기에는 바로 반영되지 않는가

현재 브라우저의 콜백과 React 상태는 그 브라우저 안에서만 동작한다. 다른 기기에 변경 사실을 알리는 식사 기록 실시간 구독이나 주기적 재조회는 구현하지 않았다. 다른 기기는 관련 화면의 재조회·대화 복원·새로고침 전까지 이전 값을 표시할 수 있다. 서버에 저장되지 않았다는 뜻은 아니다. 이는 구현 범위의 한계이며 실시간 기능을 넣으면 정확도가 낮아진다는 뜻도 아니다.

### 면접 답변 예시

> 식사 기록을 삭제한 뒤 캘린더와 상단 집계, 대화의 저장 안내가 서로 달라지는 문제를 발견했습니다. 변경 성공 후 공유 집계를 서버에서 다시 읽도록 연결했고, 대화는 저장 결과의 기록 ID로 현재 상태를 확인해 수정·삭제 여부를 표시했습니다. 공개 브라우저에서 검증 기록 한 건을 생성·수정·삭제하여 새로고침 없이 반영되는 것까지 확인했습니다. 다만 현재는 서버 확정 후 여러 조회가 이어지므로 네트워크와 DB 응답만큼 대기가 남고, 기기 간 실시간 구독은 구현하지 않았습니다. 다음에는 변경 응답에 집계와 버전을 함께 반환해 왕복을 줄이고, 실시간 이벤트는 재조회 신호로 사용하면서 누락·재연결·순서 역전을 검증할 계획입니다. 아직 그 개선 효과를 측정했다고 주장하지는 않습니다.

### 후속 개선과 정량 검증 설계 — 아직 미구현

1. 변경 요청 시작·서버 쓰기 완료·재조회 완료·상단 렌더·대화 상태 렌더 시점을 요청 ID로 연결해 먼저 계측한다. 사용자 원문과 건강 수치는 계측 로그에 넣지 않는다.
2. 변경 응답에 서버 집계·기록 버전을 함께 반환하여 후속 왕복을 줄이는 방법을 우선 비교한다. 동시 수정 시 버전 충돌·오래된 응답 무시가 필요하다. 탭 복귀 시 재조회도 별도로 검토한다.
3. 교차 기기 요구가 확인되면 사용자 범위의 실시간 이벤트를 재조회 신호로 사용한다. 접근 제어, 구독 해제, 재연결 후 재조회, 중복·누락·역순 이벤트 처리를 함께 구현한다. 이벤트 도착만으로 화면과 서버가 일치한다고 간주하지 않는다.
4. 동일한 고정 사례로 변경 전후 조건별 최소 100건을 검증한다. 수정·삭제·과거 날짜 변경·동시 수정·통신 실패·재연결 사례를 같은 비율로 유지한다. 실패·타임아웃을 분모에 포함한다.
5. 주 지표는 변경 요청→상단/대화 반영 p50·p95, 서버 쓰기 완료→화면 일치까지의 지연, 제한 시간 내 서버-화면 일치율, 실패 후 복구율, 요청 수다. 두 세션 검증에서는 다른 기기 반영 지연과 다른 사용자에게 이벤트/데이터가 전달되지 않는지도 확인한다. 합성 평가와 실제 베타 결과는 구분한다.

현재 증거는 앞서 기록한 회귀 테스트와 한 건의 공개 브라우저 기능 검증이다. 위 후속 계획의 수치 개선·교차 기기 동기화는 아직 입증하지 않았다.

## 공개 배포 검증

웹 `build-info.json`과 API `/health`가 모두 코드 커밋 `8f93fd048cec00c4262d54c48ae2e9402c05bfde`를 반환했다. Render API 자동 배포 ID는 `dep-dbaradlg1s2s73bknh0g`다.

로그인된 공개 브라우저에서 앞서 삭제한 합성 밥 10g 요약이 ‘삭제된 섭취 기록입니다. 현재 섭취량에 포함되지 않습니다.’로 바뀌고 ‘저장 당시 내역’이 구분되는 것을 확인했다. 상단도 검증 전 집계로 유지됐다. 캡처는 이 검증용 요약만 포함하며 실제 섭취·목표 수치는 공개하지 않았다.

### 사용자 승인 후 실제 브라우저 수정·삭제 검증

1. 오늘 간식에 합성 밥 11g 한 건을 확인 카드로 확정했다. 저장 전과 비교해 상단에 해당 열량(표시 16kcal)이 반영됐다.
2. 캘린더에서 그 한 건만 22g으로 수정했다. 캘린더에는 22g·32kcal가 표시됐고, 페이지 새로고침 없이 상단도 추가 분량만큼 갱신됐다.
3. 채팅 탭으로 돌아오자 ‘수정된 섭취 기록입니다’와 ‘저장 당시 내역’ 안내를 확인했다. 요약의 11g은 저장 당시 값이고 현재 값은 캘린더의 22g이다.
4. 실행 직전 삭제 확인을 받은 뒤 검증용 22g 한 건만 삭제했다. 페이지 새로고침 없이 상단이 검증 전 값으로 복원됐고, 채팅에도 ‘삭제된 섭취 기록입니다. 현재 섭취량에 포함되지 않습니다.’가 표시됐다.
5. 기존 아침 실제 기록 두 건의 음식·분량·표시 열량이 그대로 유지됨을 확인했다. 검증용 활성 기록은 남기지 않았다. 저장·수정·삭제 이력 안내는 대화에 남는다.
