# 식사 입력 화면의 보조 기능 정리 (2026-10-19)

## 목적과 변경

기본 화면에 제품 영양표·정확한 제품·점심/저녁 추천 버튼이 상시 노출되어,
단순한 식사 입력에도 먼저 선택해야 하는 필수 단계처럼 보였다.

- 첫 화면은 입력 예시와 입력창을 중심으로 정리했다. 기존 빠른 시작 메뉴도
  제거하고, 일반 음식은 그대로 기본 분량 확인 카드로 이어진다.
- 제품 영양표/정확한 제품 검색은 실제 섭취 확인 카드의 접힌
  `정확한 제품으로 변경 (선택)` 안으로 이동했다.
- 변경할 음식·g를 선택하고 기존 검색/영양표 폼을 재사용한다. 기존 식사의
  날짜·끼니·다른 음식은 유지하고 선택한 한 항목만 서버에서 다시 계산한다.
  미리 제안을 취소하거나 긴 Agent 대화를 다시 실행하지 않는다.
- 변경 중에는 분량·날짜 수정과 확정을 잠근다. 닫으면 기존 제안으로 돌아가고,
  교체에 실패하면 기존 제안과 입력값을 유지한다. 최종 확정 전 실제 섭취는 저장하지 않는다.
- 점심/저녁 추천은 실제 섭취 확정 성공 이후에만 노출한다. 계획 채택·취소·
  저장 실패·단순 상담 완료를 기록 성공으로 간주하지 않는다. 서버의 확정 결과와
  직접 저장 API의 confirmed 상태를 사용하고 답변 문구를 추측하지 않는다.

## 구현 경계

기존 MealRevision에 선택적 food_id/label 입력을 추가했다. 기존 필드는 그대로
유지하며 소유권·pending 상태·버전·체크포인트 일치 검사를 통과해야 새 제안을 만든다.
영양표는 기존 LabelNutrition 검증과 서버 환산, 제품은 공용 DB lookup을 사용한다.
다른 항목의 사용자 영양표도 보존한다. 공용 식품 DB 등록이나 새 마이그레이션은 없다.
검색은 기존 도구로 직접 수행하고, 제안 수정·확정은 기존 경계를 유지한다.

## 실패·수정과 테스트

초기 테스트는 기본 화면에 추천 버튼이 남아 있고 제품 도구가 카드 안에 없어
실패했다. 기존 API도 교체 필드가 extra_forbidden으로 거부되어 실패했다.
허용 필드만 명시적으로 확장했으며 추가 임의 필드는 여전히 거부한다.
옛 시작 메뉴의 버튼을 기대한 테스트는 삭제·skip 대신 승인된 입력 안내 검증으로 갱신했다.

독립 리뷰에서 제품 변경과 분량 수정이 동시에 가능한 초안 손실 위험을 발견했다.
실패 테스트로 재현한 뒤 편집 모드를 상호 배타적으로 만들고 내부 폼까지 busy를
전파했다. 재검토에서 해당 문제가 해소됐음을 확인했다.

- 전체 백엔드 1437 passed/기존1 skipped, 혼합 출처 교체 추가 검사 포함 관련19 passed.
- 최종 프론트 전체 115 passed/31 suites, production build 성공.
- 제품 한 항목 교체, 다른 음식·날짜 유지, 사용자 영양표 보존, 확정 전 미저장,
  실패한 저장에서 추천 미표시, 서버 확정 후 추천 표시와 상담 전송을 검증했다.
- 이번 작업은 기능·상태 전이 검증이다. 속도·정확도·이탈률 개선을 측정했다고
  주장하지 않는다. 성능 비교는 별도의 조건별100건 이상 평가가 필요하다.

## 한계

추천 버튼은 현재 화면에서 성공한 실제 섭취 확정을 기준으로 표시한다.
새로고침/새 세션에서는 상시 메뉴를 복원하지 않는다. 제품 정보 입력은 선택 기능이며
일반 음식 기록에는 필요하지 않다. 사진/인바디 및 미확인 음식 처리 기능은 유지한다.
