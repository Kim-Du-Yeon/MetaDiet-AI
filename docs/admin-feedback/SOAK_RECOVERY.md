# 실제 인증 세션·지속 부하·DB 연결 장애 복구 검증

## 검증 설계 (2026-10-15)

목표는 실제 인증된 복수 관리자의 반복 조회·동시 저장과 DB 접근 실패 후 안전한 재시도를 확인하는 것이다. 공개 서비스에 장애를 주지 않도록 운영과 같은 Supabase Auth에서 만든 임시 계정3개와 별도의 비공개 스키마를 사용한다. 로그인 JWT의 서명·사용자·서로 다른 session_id를 검증하고, FastAPI의 기존 관리자 의존성을 교체하지 않는다. 임시 이메일 allowlist는 검사 프로세스에만 적용하며 Render의 ADMIN_EMAILS는 바꾸지 않는다.

사전 판정 기준:

- 1만 건 고정 데이터에 3개 세션이 같은100개 필터·페이지 사례를 각각 실행한다(총300조회). 시작 후 최소600초 동안 6초 간격의100라운드를 진행한다. 실패·타임아웃은 삭제하지 않는다.
- 3개 JWT가 같은 버전을 수정하는 경합100회: 성공200 하나·충돌409 둘, 성공한 관리자와 일치하는 이력 한 건.
- 연결 종료, PostgreSQL statement timeout, UPDATE 후 이력 INSERT 전 연결 종료 각각100회: HTTP503·변경 롤백, 정상 연결 재시도200·중복 시도409·이력 한 번.
- 로그인 세션3개를 refresh한 토큰도 같은 관리자 API에 접근 가능해야 한다.
- 격리 스키마·임시 Auth 계정을 정리하고 결과 파일에는 자격 증명·의견 원문을 남기지 않는다.

API 호출은 로컬 ASGI transport에서 실행하고 DB는 실제 원격 PostgreSQL이다. 브라우저3개나 Render 서버의 동시 부하를 재현하는 검사는 아니다. 10분은 제한된 지속 부하 검사이며 수시간·야간 soak, 메모리 누수, 운영 용량 SLA를 보장하지 않는다. 피드백 저장소는 요청마다 연결을 생성하므로 이번 검사는 별도 LangGraph 체크포인터 pool 복구를 검증하지 않는다.

## 최종 결과

[최종 요청별 원본](soak-final.json), [소스 해시·고정 조건](soak-manifest.json), [정리·공개 정상 응답 확인](soak-cleanup-check.json). 최종 실행의 조회 구간은 **600.0초**였다.

| 검증 | 시도 | 결과 |
|---|---:|---|
| 실제 JWT 3개 세션·1만 건 조회 | 세션별100회, 총300회 | 정확성300/300, 정상 조회 오류·타임아웃0 |
| 동일 버전 동시 저장 | 100라운드·쓰기300회 | 매회200 하나·409 둘·승자 이력1건 |
| 쿼리 전 연결 종료 | 100회 | 예상503·데이터/이력 불변·재시도200·중복409 |
| PostgreSQL 쿼리 시간 초과 | 100회 | 예상503·데이터/이력 불변·재시도200·중복409 |
| UPDATE 후 연결 종료 | 100회 | 예상503·데이터/이력 불변·재시도200·중복409 |
| 실제 로그인 세션 refresh | 3회 | 새 JWT로 관리자 조회3/3 성공 |

정상 조회 전체 중앙값은 **145.45ms**, p95는 **202.92ms**였다. 세션3개의 반복 표본이며 실제 사용자300명이 아니다. 정상 조회 오류율0/300과 장애 주입의 예상503 **300/300**을 분리한다. 장애 주입은 세 조건 각각100/100 통과했고, 복구 저장300/300·중복 재시도 차단300/300이었다. 이는 자연 장애율 감소를 입증하는 실험이 아니다.

오류 로그는 연결 종료 두 유형에서 각각 `OperationalError`100건, statement timeout에서 `QueryCanceled`/SQLSTATE `57014`100건이었다. 예상한 장애 외 진단은0건이었다. 기존 코드의503 변환·트랜잭션 롤백·새 연결 재시도가 정상 동작해 운영 코드 수정이나 재배포는 필요하지 않았다.

전체 백엔드 회귀 **1084 passed·기존1 skipped**, 최종 검사 도구 단위 테스트3개 통과다. 프론트 코드가 변경되지 않아 이번 작업에서는 프론트 테스트·빌드를 다시 실행하지 않았다. 실제 UI 자동 갱신·편집 보존 검증은 [직전 보고서](SCALE_CONCURRENCY.md)에 따로 있다.

[초기 실행 원본](soak-initial.json)은 이력 불변 판정 보강 전의 도구 결과로 보존하며 최종 통과 근거에서 제외한다. 초기·최종 수치는 성능 전후 비교로 사용하지 않는다. 두 실행에서 생성한 임시 Auth 계정·스키마가 남지 않았음을 최종 읽기 검사로 확인했다. 공개 API와 웹은 종료 후에도HTTP200이었다. 실제 피드백·섭취 기록과 배포 관리자 allowlist는 변경하지 않았다.

## 재현

```powershell
backend\venv\Scripts\python.exe backend/scripts/check_feedback_soak.py
backend\venv\Scripts\python.exe -m pytest backend/tests -q
```

프로젝트의 git-ignored backend/.env에서 자격 증명을 읽는다. 중간 정리를 위한 임시 식별자는 git-ignored backend/.env.feedback-soak에 보관하고 성공적으로 정리하면 제거한다. 보고서는 backend/artifacts/feedback-soak.json에 저장한다. 운영 사용자나 섭취 기록을 만들거나 수정하지 않는다. 스키마 LIKE 복제는 외래 키를 복제하지 않으므로 운영 FK 통합 검증과 구분한다.

## 범위 밖

DB 전체 중단·재시작, 리전 장애, 백업/PITR 복원, 커밋 성공 직후 응답이 유실되는 상황, 여러 실제 브라우저 탭의 장시간 UI 상태, 토큰 자연 만료까지의 수시간 실행은 수행하지 않는다. 이를 검증하려면 별도 staging DB·배포와 더 긴 실행 창이 필요하다. 이번 결과를 재해 복구 RTO/RPO로 해석하지 않는다.


## 검증 도구 리뷰와 실패 처리 보완

초기 도구 리뷰에서 실패 후의 이력 건수만 읽으면 실패 중 생긴 잘못된 이력을 기준값으로 받아들일 수 있음을 발견했다. 장애 전 이력 건수를 먼저 기록하고, 실패 후 동일한지와 복구 후 정확히 한 건 증가하는지를 각각 확인하도록 수정했다. 이력 불변 판정 플래그 누락이 통과되지 않도록 단위 검사를 추가했다.

Auth 생성 요청은 스레드에서 실행되므로 호출자를 취소해도 원격 생성이 끝날 수 있다. [asyncio shield·취소 처리 공식 문서](https://docs.python.org/3/library/asyncio-task.html#shielding-from-cancellation)를 확인하고 생성 작업의 완료 결과를 회수한 뒤 정리 대상에 기록하도록 보완했다. 응답 자체가 유실되는 경우도 고려해 생성 전 임시 이메일을 비공개 env manifest에 남기고, 필요할 때만 제한된 페이지 조회로 정확히 일치하는 계정을 찾아 정리한다. 다른 사용자는 삭제 대상에 넣지 않는다. 복구 조회가 실패하면 정리 성공으로 판정하지 않는다. 취소·응답 유실·다른 사용자 제외를 단위 테스트로 검증했으며 실제 Auth 장애가 발생했다고 주장하지 않는다.

초기 단위 재현 실행에는 종료되지 않는 대기 상태가 남아 해당 테스트 프로세스만 종료했다. 함수 참조를 대기 전에 확인하도록 검사 코드를 보완했으며, 그 대기의 원인을 서비스 결함으로 판정하지 않았다. 제품 테스트를 삭제하거나 스킵하지 않았다. 리뷰로 보완한 도구를 최종 전체 실행으로 재검증하고, 초기 실행의 수치는 최종 판정에서 분리한다.


## 해석 시 주의

조회 시간은 이미 로그인·JWT 검증 준비·스키마 생성·데이터 적재가 끝난 뒤 측정한다. HTTPX의 로컬 ASGI 호출과 실제 원격 DB 새 연결 비용을 포함하며 로그인 시간이나 Render의 네트워크 지연은 포함하지 않는다. 동시성은 6초마다3개 요청이 겹치는 수준(평균 약0.5조회/초)이며 최대 처리량을 찾는 부하 시험이 아니다. 이전 도구와 이번 도구는 인증·부하 조건이 달라 지연 수치를 개선 전후로 비교하지 않는다.

장애 주입의 HTTP503은 예상된 결과다. 정상 조회의 실패율과 구분하고, 장애 요청을 제외해 전체 신뢰도가 높아졌다고 주장하지 않는다. 복구는 다음 정상 연결의 요청이 성공함을 뜻하며 장애부터 복구까지의 운영 RTO는 측정하지 않는다. UPDATE 후 연결을 클라이언트에서 닫는 상황은 미커밋 트랜잭션 롤백 검사이고, 커밋 성공 여부를 알 수 없는 응답 유실과는 다르다.
