# 모델 생성 병목: 후속 코칭 프롬프트 축소 실험

2026-10-14. 기존 공개 100건의 단계별 로그를 분석하고 가장 큰 단일 처리 단계인 모델 생성을 대상으로 변경 하나를 비교했다.

## 문제와 가설

기존 [공개 100건](../latency100/after.json)의 단계별 중앙값은 meal 모델 생성 **4.444초(n=96)**, 실행 예산 저장 **2.456초(n=100)**, DB 조회 **0.490초(n=95)**, 마지막 체크포인트 **0.217초(n=100)**였다. 관측 항목이 없는 요청을 0으로 대체하지 않았다. `graph_total`, `budget_storage` 등의 상위 단계는 내부 단계와 중첩되므로 중앙값을 더해 전체 시간을 만들지 않는다. [원본 해시와 집계](baseline_stages.json).

현재 Gemini3.8 Flash는 `low`보다 낮은 `minimal`을 지원하지 않는다([공식 모델 문서](https://ai.google.dev/gemini-api/docs/latest-model)). 그래서 추론 수준이나 모델을 바꾸지 않고, 단순 후속 코칭에 필요 없는 식품 제품 선택·저장 제안 작성 지시만 줄였다. 출력 토큰을 강제로 잘라 속도를 얻는 방식은 사용하지 않았다([공식 thinking 안내](https://ai.google.dev/gemini-api/docs/generate-content/thinking)).

## 변경 범위

`COMPACT_FOLLOWUP_PROMPT`는 기본 비활성인 실험 설정이다. 기존의 단순 후속 질문 판정과 현재 요청의 최신 DB 조회가 모두 통과해야 축소 프롬프트를 사용한다. 첫 추천, 복잡한 질문, 확인 대기 제안, 기록 변경, Supervisor 경로는 그대로다.

현재 목표·섭취량 우선, 기록 없음과 금식 구분, 읽기 전용 도구, 수치 근거 제한, 특수 대상 개별 처방 금지, 저장 완료 허위 주장 금지, 최종 근거 검증은 유지한다. 사용자 기록을 요청 사이에 캐시하지 않는다.

## 실험 설계

- 실제 Gemini3.8 Flash/low를 두 조건 모두 사용하며 도구·대화 문맥·최종 검증은 같다.
- 이전 실험과 동일한 4개 후속 질문×5개 현재 상태×5회로 **조건별100건, 총200건**을 새로 실행했다. 과거 시간을 이번 대조군으로 재사용하지 않는다.
- 한 쌍마다 실행 순서를 번갈아 바꾼다. 실패·시간 초과·초기 provider 준비가 포함된 첫 요청도 삭제하지 않는다.
- 현재 DB는 합성값이며 이전 대화의300kcal/2200kcal와 의도적으로 다르다. 확정·수정·삭제·목표 변경·새 날짜 상태를 모사한다. 실제 사용자 날짜 경과를 관찰한 실험은 아니다.
- 최신값 검사는 응답에 현재 섭취량과 목표가 정확히 출력되는지 확인한다. 저장 여부는 repository 호출과 pending proposal을 검사한다.
- 동일 자동 judge에 조건·시간을 숨기고 전체 답변을 판정한다. 임상 정확도 인증이나 독립 인간 평가로 표현하지 않는다.

사전 채택 기준: 중앙값10% 이상 감소, p95 악화10% 이내, 완료·최신값·미저장·품질 통과 건수 비악화. 기준 미달 시 운영 기본값을 바꾸지 않는다. 로컬 실행 시간에는 실제 공개 네트워크·운영 DB·체크포인트 비용이 포함되지 않으므로 공개 전체 응답시간 개선으로 주장하지 않는다.

## 결과와 채택 결정

| 지표 | 기존 100건 | 축소 후보 100건 |
|---|---:|---:|
| 완료 시간 중앙값 | 4.323초 | 4.413초 |
| 완료 시간 p95 | 7.320초 | 6.112초 |
| 입력 토큰 중앙값 | 1,357 | 887 |
| 출력 토큰 중앙값 | 108.5 | 123.5 |
| 요청 완료 / 최신 수치 반영 | 100/100 | 100/100 |
| 저장 없음 | 100/100 | 100/100 |
| 자동 품질 판정 5항목 각각 | 100/100 | 100/100 |

품질 5항목은 질문 관련성, 실행 가능한 조언, 섭취 사실 비조작, 허위 저장 주장 없음, 간결성이다. 200건 모두 judge 판정을 완료했으며 오류·재시도는 없었다. 단일 자동 judge 결과이고 실제 사용자 만족도나 임상 정확도가 아니다. 최종 백엔드 회귀는 **961 passed, 기존 1 skipped**이며 이번 변경에서 프론트 코드는 수정하지 않아 프론트 테스트·빌드를 재실행하지 않았다.

**속도 가설은 채택하지 않는다.** 중앙값이 약 2.1% 늘어 사전에 정한 10% 감소 기준을 충족하지 못했다. p95는 약 16.5% 감소하고 입력 토큰은 약 34.6% 줄었지만, 유리한 지표만 골라 운영에 적용하지 않는다. `COMPACT_FOLLOWUP_PROMPT=False`를 유지한다.

실행 실패는 없었으며 실패한 것은 성능 개선 가설이다. 입력 축소가 전체 시간을 지배하지 못했고 출력 토큰 중앙값도 증가했다. [Gemini 공식 문서](https://ai.google.dev/gemini-api/docs/long-context)는 입력 길이와 무관한 고정 지연도 있다고 설명한다. 이 결과는 입력 토큰 감소가 완료 시간 감소를 보장하지 않는다는 근거이며, 공급자 대기·네트워크·내부 추론 중 무엇이 정확한 원인인지는 현재 로그로 분리할 수 없다. 출력 제한이나 최신 DB 조회 생략으로 수치를 억지로 낮추지 않았다.
