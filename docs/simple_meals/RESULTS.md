# 간단한 식사 입력과 하루 코칭

기준일: 2026-10-13. 실제 사용자 성과가 아닌 구현 검증과 합성 입력 평가다.

## 사용자 흐름

`닭가슴살 밥 한공기 김치` → 삶은 닭가슴살 100g·백미밥 200g·배추김치 40g 확인 카드 → 필요하면 분량·단위·날짜·끼니 수정 → 서버 재계산 → **이대로 기록**.

기본 분량은 앱의 편의 설정이며 보편적인 실측값이나 의학적 기준이라고 주장하지 않는다. 명시한 g가 개수·공기보다 우선한다. 생것·구운것을 명시하면 해당 CSV 항목을 사용한다. 라이스페이퍼는 검토된 식약처 대표 항목 `P108-007000300-0013`과 1장 10g 앱 기본값으로 계산하고 대략값임을 표시한다. 특정 제조사 제품을 먹었다고 추정하지 않는다.

기본 카드에는 음식별 kcal·탄수화물·단백질·지방, 합계, 오늘 확정 섭취량과 구분한 기록 후 남는 칼로리를 표시한다. 출처·제조사·나트륨은 상세 정보에 둔다. 제품을 정확히 입력하는 경로는 보조 기능으로 유지하며 비활성 버튼의 사유를 표시한다. 점심·저녁 추천은 기존 코칭 경로를 사용하고 계획 채택은 실제 섭취량으로 저장하지 않는다.

## 구현 경계

- 전체 입력이 검토된 음식·분량 문법에 해당할 때만 빠른 계산 경로를 사용한다. 알려지지 않은 음식이나 추천·복합 요청을 일부만 파싱해 저장하지 않는다. 해당 요청은 기존 Agent 확인 흐름으로 돌아간다.
- 검토된 별칭은 닭가슴살·백미/현미밥·배추김치·삶은 달걀·구운 고등어/삼겹살·바나나·두부·라이스페이퍼와 닭가슴살 조리 형태다. 모든 음식의 자연어를 지원한다고 주장하지 않는다.
- 영양값은 DB와 서버 계산만 사용한다. 표시 분량은 기존 nutrition_metadata에 보존하여 마이그레이션이 필요 없다.
- 분량 수정 API는 사용자 소유권·pending 상태·버전·날짜·단위를 검증한다. 클라이언트가 영양값이나 식품 ID를 바꾸는 요청은 받지 않는다. 단위가 있는 음식은 그 기준량으로 다시 조회한다.
- 빠른 경로도 LangGraph 안에서 pending proposal을 생성하고 기존 승인·중복 방지 정책을 사용한다. 실행 예산의 논리 도구 2회는 **배치 조회/계산**과 **제안 준비**다. 개별 Python 함수 호출 횟수와 구분한다.

## 동일 버전 경로 비교

고정 요청 3개를 각각 3회, 경로당 9회 실행했다. 실행 순서를 번갈아 적용하고 실제 Gemini를 사용했다. 제안은 메모리에만 보관했으며 건강 데이터 DB에 쓰지 않았다. 원본과 실행 스크립트: [COMPARISON.json](COMPARISON.json), [평가 스크립트](../../backend/scripts/eval/run_simple_meal_comparison.py).

| 지표 | 기존 Agent 경로 | 간단 계산 경로 |
|---|---:|---:|
| 요청 수 | 9 | 9 |
| 모델 호출 중앙값 | 3 | 0 |
| 논리 도구 호출 중앙값 | 4 | 2 |
| 로컬 실행 중앙값 | 15.389초 | 0.203초 |
| 즉시 확인 제안 생성 | 0/9 | 9/9 |
| 기대 분량과 일치 | 0/9 | 9/9 |
| 제품 선택 요구 | 3/9 | 0/9 |

기존 응답 원문을 검토했을 때 9회 모두 분량·끼니 또는 제품 선택의 추가 확인이 필요했다. 새 경로에서는 추가 질문 없이 확인 카드가 생성됐다. 저장 승인 버튼은 추가 정보 질문으로 세지 않는다.

이 수치는 **동일 버전의 빠른 경로 활성/비활성 비교**다. 과거 커밋이나 약 100초 장애의 역사적 전후 비교가 아니다. 로컬 CSV 구성·원격 식품 조회는 포함하고 HTTP·영구 proposal 저장·Render 휴면 복구는 제외한다. 9개 표본에서 p95나 실제 제품 사용자 성과를 주장하지 않는다.

## 실패와 수정

1. 빈 식단 목록에서 첫 끼니를 읽어 프론트 테스트가 실패했다. [React 조건부 렌더링 문서](https://react.dev/learn/conditional-rendering)를 확인하고 빈 목록을 안전하게 처리했다.
2. 기본 닭가슴살을 생것에서 삶은 것으로 변경하자 이전 golden test가 실패했다. 실제 CSV의 삶은 닭가슴살 200g(254kcal, 단백질 56.2g)로 기대값을 갱신했다. 임의 수치로 변경한 것이 아니다.
3. Windows 공용 임시 디렉터리에서 WinError 5가 발생했다. [pytest 임시 경로 문서](https://docs.pytest.org/en/stable/how-to/tmp_path.html)에 따라 작업 전용 basetemp로 재검증했다. 테스트를 삭제하거나 새로 skip하지 않았다.
4. 읽기 전용 코드 검토에서 원래 분량으로 되돌려도 확정이 막히는 오류, 다중 끼니 계획의 끼니 덮어쓰기, proposal 저장 후 체크포인트 실패 시 복구 불가를 발견했다. 실제 draft 차이로 버튼을 제어하고 기존 끼니를 보존하며 새로 불러오기에서 최신 pending proposal을 동기화했다. [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence)의 thread/checkpoint 경계를 유지한다.

5. 공개 카드에서 라이스페이퍼 80g이 91.2kcal·탄수화물 3.2g·지방 7.2g으로 표시돼 대표 항목을 재검토했다. 활성 식약처 원본 자체에 기존 코드 `0016`의 100g당 114kcal·탄수화물 4g·지방 9g이 들어 있었다. 환산 오류로 단정하지 않고 이름만으로 대표를 정한 기준이 부적절하다고 판단했다. [식약처 기준량 안내](https://various.foodsafetykorea.go.kr/nutrient/industry/meal/list.do)와 후보의 기준량·수치를 비교해 검토한 건조 피 항목 `0013`(100g당 340kcal·탄수화물 85g·단백질 0.5g·지방 0g)으로 교체했다. 실제 먹은 브랜드가 확인됐다고 주장하지 않는다. [두 원본 행](RICEPAPER_REVIEW.json)을 보존하고 단위 테스트·전체 pytest·경로 비교와 공개 카드까지 재검증했다.
6. 공개 테스트 계정 초기 설정 요청이 배포 중 HTTP 502로 실패했다. [Render 배포 문제 해결 문서](https://render.com/docs/troubleshooting-deploys)를 확인하고 새 배포 Live 및 health 200을 확인한 뒤 같은 계정의 설정 요청을 재시도해 성공했다. 배포 시점과 상관관계는 확인했지만 내부 게이트웨이 원인을 단정하지 않는다.
