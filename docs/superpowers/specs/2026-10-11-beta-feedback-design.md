# MetaDiet AI 인앱 베타 피드백 설계

## 1. 목적과 범위

제한 베타 사용자가 앱 안에서 짧은 의견을 제출하고, 운영자가 이를 재현 가능한 개선 사례로 분류할 수 있게 한다. 피드백 제출 자체가 건강정보·대화 원문을 새로 수집하는 경로가 되지 않도록 최소 정보만 저장한다.

이번 범위는 인증된 사용자의 수동 제출, 안전한 저장, 성공·실패 UI와 운영 검토 절차까지다. 관리자 대시보드, 자동 LLM 요약, 이메일 발송, 첨부파일, 스크린샷, 전체 대화 자동 첨부는 제외한다.

## 2. 검토한 접근과 선택

### 선택: 앱 내부 최소 피드백

설정 화면에서 만족도, 유형과 짧은 의견을 받아 자체 Supabase에 저장한다. 인증·RLS·입력 검증을 현재 서비스 경계와 동일하게 적용할 수 있고, 외부 폼 계정이나 별도 개인정보 처리자를 추가하지 않는다.

### 제외: 외부 설문 링크

구현은 빠르지만 사용자가 앱을 벗어나며 외부 서비스의 개인정보 정책과 사용자 식별 연결 방식을 추가로 관리해야 한다.

### 제외: 대화별 좋아요·싫어요와 trace 자동 연결

정밀 분석에는 유리하지만 모든 메시지 UI와 trace 식별 정책이 바뀌고 건강정보가 의도치 않게 피드백 데이터에 결합될 가능성이 있다. 제한 베타의 작은 범위를 넘는다.

## 3. 사용자 흐름

1. 인증 사용자가 계정 설정의 `BETA FEEDBACK` 카드를 연다.
2. 만족도 1~5점, 유형 하나, 의견을 입력한다.
3. 화면에는 대화·식사·인바디 원문이 자동 첨부되지 않는다고 안내한다.
4. 제출 시 버튼을 잠그고 API 결과를 기다린다.
5. 성공하면 입력을 초기화하고 `피드백을 저장했습니다` 상태를 표시한다.
6. 네트워크·검증·서버 오류는 사용자가 다시 시도할 수 있는 짧은 메시지로 표시하고 입력값은 유지한다.

유형은 `general`, `answer_quality`, `evidence`, `usability`, `bug`의 고정 enum을 사용한다. 의견은 선택 사항이지만 만족도와 유형은 필수다. 같은 내용을 여러 번 자동 재시도하지 않는다.

## 4. 데이터 모델과 보안

새 테이블 `beta_feedback`을 추가한다.

| 필드 | 형식 | 규칙 |
|---|---|---|
| `id` | UUID | 서버 생성 PK |
| `user_id` | UUID | 내부 `users.id` FK, 삭제 시 cascade |
| `rating` | smallint | 1~5 check |
| `category` | text | 허용 enum check |
| `comment` | text | nullable, trim 후 최대 1,000자 |
| `page` | text | 서버 허용값 `settings`만 저장 |
| `client_submission_id` | UUID | 사용자별 unique, 중복 제출 멱등성 |
| `created_at` | timestamptz | DB 기본 현재 시각 |

RLS를 활성화한다. 인증 사용자가 Supabase 브라우저 클라이언트로 테이블을 직접 쓰는 경로는 제공하지 않는다. 서비스 API는 JWT에서 내부 사용자 ID를 조회해 insert하며, 사용자 ID를 요청 본문에서 받지 않는다. 관리자 조회 API는 이번 범위에서 만들지 않는다.

저장하지 않는 항목:

- 이메일, 이름, 비밀번호
- 식사·인바디·목표 값
- 대화 원문이나 Agent 응답 원문
- LangSmith trace 내용
- IP·브라우저 fingerprint

## 5. API 계약

`POST /feedback`을 추가한다.

요청:

```json
{
  "rating": 4,
  "category": "answer_quality",
  "comment": "근거 설명은 좋지만 첫 응답이 느렸습니다.",
  "client_submission_id": "UUID"
}
```

응답은 새 저장이면 `201`, 같은 사용자·submission ID 재전송이면 기존 ID를 반환하는 `200`이다. 인증 없음은 `401`, 검증 오류는 `422`, 저장소 일시 실패는 원문 예외를 노출하지 않는 `503`을 반환한다.

서버는 comment의 앞뒤 공백을 제거하고 빈 문자열은 null로 저장한다. HTML을 실행하지 않으며 운영 검토 시에도 plain text로 취급한다. 로그에는 feedback ID, category, rating과 성공 여부만 남기고 comment를 남기지 않는다.

## 6. 프론트엔드

기존 `Settings.jsx`에 독립 `BetaFeedbackCard` 컴포넌트를 배치한다. 계정 삭제 상태와 피드백 입력 상태를 분리해 Settings의 단일 책임이 더 커지지 않게 한다.

구성:

- 접근 가능한 1~5 라디오 그룹
- 유형 select와 한글 표시명
- 최대 1,000자 textarea 및 남은 글자 수
- 제출 중 disabled 상태
- `role=status` 성공·실패 메시지
- 개인정보 최소 수집 안내

API 호출은 `dietApi.js`의 기존 bearer token 패턴을 재사용한다. `client_submission_id`는 제출 버튼을 처음 누를 때 생성하고, 네트워크 재시도 중에는 같은 값을 유지하며 성공 후 새 값으로 초기화한다.

## 7. 오류 처리와 관측

- Supabase insert 예외는 구조화 로그에 오류 유형과 feedback ID만 남긴다.
- comment나 사용자 건강정보를 로그와 LangSmith에 전송하지 않는다.
- DB가 사용할 수 없으면 503으로 실패하고 로컬 브라우저에 성공 상태를 남기지 않는다.
- 사용자 삭제는 FK cascade로 피드백도 삭제한다. 계정 삭제 감사 스크립트에 테이블 포함 여부를 검사한다.
- API 자동 재시도는 하지 않는다. 프론트 사용자가 다시 제출할 때 같은 submission ID로 멱등 처리한다.

## 8. 검증

백엔드:

- 인증 없이는 제출할 수 없다.
- JWT 사용자가 다른 `user_id`로 저장할 수 없다.
- rating·category·comment 길이 검증.
- 동일 submission ID가 중복 row를 만들지 않는다.
- DB 오류가 comment나 내부 예외를 응답·로그로 노출하지 않는다.
- 계정 삭제 대상 테이블에 피드백이 포함된다.

프론트엔드:

- 필수 입력과 1,000자 제한.
- 제출 중 중복 클릭 차단.
- 성공 시 초기화, 실패 시 입력 유지.
- 접근 가능한 label·radio·status.
- API가 bearer token과 submission ID를 보낸다.

통합:

- 합성 사용자로 공개 또는 로컬 제출 후 Supabase row 확인.
- 같은 submission ID를 두 번 보내 row 한 건 확인.
- 합성 계정 삭제 후 feedback row 삭제 확인.
- 전체 backend pytest, frontend test와 production build 통과.

## 9. 배포와 완료 기준

1. additive SQL migration 적용.
2. API 배포와 health 확인.
3. 정적 UI 배포.
4. 합성 사용자 성공·중복·삭제 흐름 확인.
5. 개인정보 안내에 베타 의견의 수집 항목·목적·삭제 경로 추가.
6. 실패 사례를 재현할 때 사용자가 명시적으로 작성한 comment만 사람이 검토하고, 자동으로 대화 원문과 결합하지 않는다.

완료 기준은 인증된 사용자가 개인정보 원문 자동 첨부 없이 피드백을 제출하고, 중복·오류·계정 삭제 경계를 테스트로 증명하는 것이다.
