## 무엇을 위한 작업인가

LangSmith에서 수정한 후속 상담 프롬프트 v2를 운영에 적용하기 전에 v1과 비교하는 단계다. 목표는 불필요한 추가 입력 요구를 줄이면서 꼭 필요한 확인 질문과 최신 기록 반영은 유지하는 것이다. 프롬프트 버저닝·후보/평가/서명 연결은 구현했으며, 현재 막힌 부분은 **평가자가 반환한 점수를 안정적으로 읽는 작업**이다.

'승인 기준 미충족'은 새 후보의 개선과 안전성을 사전 기준으로 확인하지 못해 승격하지 않았다는 뜻이다. 정확성+충실성98/100 이상, 필수 질문48/50 이상, 불필요한 요구5건 이상 감소, p95/생성비1.25배 이내 등의 기준을 유지한다. 답변 오류 일부를 허용하되100쌍의 채점 근거는 검증돼야 한다. 아직 전체 품질 점수를 주장하거나 v2가 더 좋다고 결론 내리지 않는다. 운영 signed v1과 실제 사용자 A/B OFF는 유지한다.

## 46쌍 원문 분석

| 원문 상태 | 건수 | 처리 |
|---|---:|---|
| a/b 안의 이름 없는7원소 배열 | 42 | 필드 순서 추측 금지, 미복구 |
| 루트 배열/배열로 감싼 응답 | 2 | 필드 이름 부족, 미복구 |
| 필수 boolean이 null | 1 | true/false 대입 금지, 미복구 |
| 명명된12개 점수+공통 설명 | 1 | 점수 그대로 복구, 공통 설명 출처 명시 |

46개 모두 JSON 구문은 읽혔고 finish_reason은 STOP이다. JSON 문법 오류·토큰 상한 중단으로 단정하지 않는다. 문제는 출력 스키마와 점수 의미 연결이다. 설명 문장을 읽고 점수를 재판단하거나, 배열의 위치를 필드에 대응시키지 않았다. answer_now 사례의 null도 false로 바꾸지 않았다.

복구 사례 `cb2-eval-missing_referent-03`은 각 a/b의6개 점수가 전부 이름과 boolean 타입으로 명시돼 있었다. 설명만 하나의 reason에 공통으로 주어져 이를 그대로 참조했다. 각 점수의 JSON pointer와 공통 이유의 `/reason` 출처를 기록했다. 양쪽에 독립적으로 작성된 설명처럼 주장하지 않는다. 기준·점수·사용량·비용은 바꾸지 않았다.

## 추가 호출이 필요하다면

배열/누락된 점수는 원문만으로 확정할 수 없으므로 전체 점수를 얻으려면 남은45쌍의 **평가만** 다시 요청해야 한다. 기존200개 답변과 유효55쌍은 재생성·재채점하지 않는다. 원래 실패 기록도 보존한다. 평가 질문·rubric·모델을 바꾸면 기존 채점과 동일 평가인 것처럼 섞지 말아야 한다.

추정은 기존 유효 Batch 출력의 평균 실제 사용량 기반 비용에45를 곱한 값이다. 확정 견적이나45쌍 성공 보장이 아니며 thinking·출력 길이에 따라 달라진다. Gemini3.1 Pro Batch의200K 이하 입력 단가는100만 토큰당 입력$1/출력(추론 포함)$6이다. [공식 요금](https://ai.google.dev/gemini-api/docs/pricing.md). 최대 예약은 평균 실비보다 크므로 작은 묶음으로 예약→정산해야 한다. 제안한$0.25를 실제로 적용한다면 먼저2쌍만 별도 최대예약 약$0.04 안에서 확인하고, 형식 실패 때 대량 재호출하지 않는 방식이 적절하다. 이 문서는 실행 승인이 아니며 이번에는 추가 유료 호출을 하지 않았다.
