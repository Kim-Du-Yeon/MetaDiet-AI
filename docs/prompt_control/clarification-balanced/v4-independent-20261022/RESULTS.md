## 승인·운영 판단

사전 승인 기준 통과: **False**. 미통과 항목: **both100_normal_completed_and_graded_accounted**.

사전 기준은 비교 기준선까지100건 정상 완료를 요구한다. v1의 최신 기록 사례2건이 모델3회 사용 후 blocked되어 이 완료 조건을 충족하지 못했다. 결과를 본 뒤 기준을 완화하지 않았으며, **서명·Staging·Production 승격과 후보 공개 브라우저 검증은 수행하지 않았다. 기존 운영v1 유지**는 v1의 점수가 더 높다는 뜻이 아니다. 후보 품질 지표와 운영 승인 조건을 분리해서 해석한다.

이번 기준선 전건 정상 종료 조건은 후보 자체가 통과하더라도 승격을 막는 설계상 제약이다. 향후에는 후보의 절대 안전·품질 기준과 기준선 실패 포함 비교를 분리해 사전에 정하는 것이 적절하다. 이 결과를 사후 기준 변경의 통과 결과로 바꿔 적지 않는다. 추가 생성을 반복하지 않았다.

## 회복·회귀와 차단 원인 범위

전체 행동 회복8건, 회귀0건. ID·양쪽 원문·각 판정은 위 전체 사례 파일에 포함했다.

[차단2건의 원문·호출 흐름](generation-failures.json): h5-stale-06/08은 v1에서3회 사용 후 blocked, v4에서는1회로 현재값 계산을 완료했다. 마지막 AgentResult.reason과 모델 출력은 실행기가 저장하지 않아 정확한 종료 원인을 확정할 수 없다. 단순히 동일 도구를 반복한 버그로 단정하지 않는다. 모델 호출 제한을 높이거나 실패 응답을 재생성하지 않았다.

## 두 프롬프트 조합 승인 경로

기존 CLI가 이 suite를 검토된 어댑터로 전달하도록 연결했다. 허용 범위는 동결한 v4의 team.base+team.compact_followup 조합이며 나머지6개는 승인된 기준선 그대로다. 정확한8커밋·본문·입력·답변과 채점 binding·Pro 원문 엄격 재파싱·정상 종료 사유·usage·실제 두 프롬프트 실행을 확인하고 원본에서 기준을 다시 계산한다. 임의의 다른 변경 경로는 계속 거부한다.

합성 단위 fixture에서는 승인·receipt 재검증 성공과 답변/매핑/원문/실제 프롬프트 적용/비용/종료 사유 변조 거부를 검증했다. 이는 실제 후보 승인 성공이나 운영 제어 검증이 아니다. 실제 후보는 evaluate에서 거부되며 서명 키와 원격 배포 단계로 넘어가지 않는다.

[승인 검증 보강 증거](approval-hardening-proof.json): 생성 완료 뒤 verify와 code_sha만 보강했다. 전체200답변 행·후보·사례·판정 기준·usage는 동일하고 이전 코드/메타데이터는 approval-hardening-originals에 보존했다. 재사용 평가 helper12개의 불변 원본도 기존8bba8d81과 일치한다. 새 모델 호출은 없었다. SDK/라이브러리 버전도 검사한다. 이는 외부 모델 실행의 암호학적 attestation이 아니라 운영자의 잘못된 결과 연결을 막는 승인 체계다.

## 실행 프롬프트 검증의 조립 계약 보완

등록 텍스트 뒤에 실제 런타임이 담당 역할·근거 지시문을 붙이는 경로를 최초 검증기가 전체 문자열 일치로 오인했다. 이 거부 원문과 이전 코드를 prefix-validation-originals에 보존했다. 등록 텍스트가 시스템 지시문 선두에 있어야 하며, 두 버전 중 가장 긴 일치 텍스트를 사용해 v1이 확장된 v4 텍스트를 빌려 통과하지 못하게 했다. 템플릿별 적용은 사례마다 한 번만 센다. [변경 증거](prefix-validation-proof.json). 품질 점수·기준·후보·생성200행·채점100행은 동일하고 추가 모델 호출0이다. 최종 실제 evaluate는 문자열 비교 오류가 아니라 기준선의 미완료 실행 때문에 거부된다. [실제 거부](approval-rejection.json).

[운영/Staging 실제 원격 readback](channels-after.json)은 두 채널 모두 기존v1이며 Production의 전체8커밋이 기존과 동일함을 확인한다. 후보 공개 브라우저 검증은 하지 않았다.
