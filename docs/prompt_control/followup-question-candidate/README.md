## 실패 조사와 수정

- `GoogleRateLimitError`를 저장한 두 Pro 시도는429로 식별했지만, 기존 안전 로그에는 RPM/TPM/RPD 세부 quota metric이 없어 범위를 확정할 수 없다.402 크레딧 소진이라고 단정하지 않았다. [Gemini 공식 재시도 안내](https://ai.google.dev/gemini-api/docs/troubleshooting#retry-strategy)에 따라 한 차례 간격을 둔 재개만 시도한 뒤 중단했다. 실패행을 지우거나 완료로 덮어쓰지 않았다.
- 과거 baseline 답변을 새 report로 옮길 때 서명 승인 메타데이터가 덧붙은 명세를 연결해 원래 행의 bundle digest와 달라지는 문제를 발견했다. 프롬프트 본문과 실제 답변은 같지만 raw report는 자동 승인 증거로 사용할 수 없다. 원본은 그대로 보존하고 재사용 어댑터를 원래 실행 snapshot 보존으로 수정했다. 실패 재현 테스트 후 관련19개 통과. 답변·채점 binding을 사후 조작해 승인을 통과시키지 않았다.
- 전체 회귀의 첫3실패는 긴 Windows 임시 경로의 `WinError206`/파일 생성 실패였다. [공식 MAX_PATH 설명](https://learn.microsoft.com/en-us/windows/win32/fileio/maximum-file-path-limitation)을 확인하고 짧은 basetemp로 실행해1708통과·기존 선택 skip1을 확인했다. 테스트를 삭제/스킵하지 않았다. UI 변경이 없으므로 기존 프론트132통과/빌드 결과를 새 실행 결과로 중복 주장하지 않는다.
