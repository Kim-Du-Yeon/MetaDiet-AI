### 캐시 비교와 적용 범위

RAG 실험은 동일한 공개 검색 문맥이 반복될 때만 해당 문맥을 재사용한다. 매번 새 검색 결과를 캐시에 넣거나 전체 문서를 추가하지 않았다. 동결 질문/문맥·같은 Flash3.8·temperature0·low thinking·max1024·동시성1, prefix별 묶음 순서와 사례 내 AB/BA를 고정했다. 질문은 동적으로 전달하고 모델 클라이언트를 양쪽에서 동일하게 재사용한다. 일반 호출에도 암묵적 캐시가 활성화되어 있으므로 ‘캐시 완전 OFF’ 비교가 아니다. 전체 Agent·검색 지연이 아닌 검색 후 생성 경계 실험이며 실제 트래픽의 문맥 재사용 빈도를 뜻하지 않는다.

[캐싱 원본200시도](cache-rag/paired.json) · [동결100사례](cache-rag/frozen.json) · [독립 Pro 평가](cache-rag/judges.json) · [최종 집계](cache-rag/summary.json). 최초 생성과 재사용, 첫 토큰과 전체 지연, 실패·미채점·불명 비용을 구분한다. 캐시 생성은 입력 정가를 보수적 상한으로 더하고 TTL300초 전체 보관료를 포함했다. 별도 생성료가 실제 청구된다고 주장하지 않으며 실제 청구서는 확인하지 않았다.

개인 캐시 운영 훅/계정 삭제 연결·다중 워커 공유 lease·내구성 삭제 큐는 미적용이다. 합성100회 테스트에서 최신 동적 입력·사용자/대화/릴리스/수정 버전 격리를 검사했지만 실제 개인 캐시 운영 검증이 아니다. 기능 플래그는 OFF이며 현재 서비스에서 개인 대화를 이 명시적 캐시에 업로드하지 않는다. 개인 캐시의 유료 전후100쌍 성능 비교도 완료로 표시하지 않는다.

## 안전한 운영 제어

- 8개 프롬프트는 각각 비공개. 9번째 비공개 `metadiet-release-manifest`가 전체 실제 커밋/해시/변수/출력 계약을 고정한다. 원격 Runnable/모델/도구를 역직렬화하지 않는다.
- LangSmith 화면의 개별 프롬프트 수정은 초안이다. 검증·서명된 완전한 릴리스 명세만 Staging/Production으로 승격한다. 코드의 저장 승인·소유권·루프 제한은 프롬프트가 바꾸지 못한다.
- 60초 비동기 갱신/관리자 강제 갱신. 요청·진행 중HITL은 이전 스냅샷을 유지한다. 실패하면 마지막 정상 버전, 첫 부팅은 로컬v1. Render 교체 시 임시 파일이 보존된다고 가정하지 않는다.
- A/B 실제 배정은 별도 승인 전OFF. 프롬프트별 독립 태그를 운영에서 조합하지 않는다.
- 승인된v1의 메타데이터 전용 별칭 `v1-control-drill`은 동일한8개 커밋/문구로 승격·롤백을 점검하기 위한 것이다. 미통과v2를 운영에 넣는 실험이 아니다.

## 재실행

프로젝트venv로 `backend/scripts/eval/benchmark_prompt_control.py --allow-paid`, 저장 답변만 채점하는 `judge_prompt_control.py --allow-paid`, 오프라인 `analyze_prompt_control.py` 순서다. 기존 결과는 재사용하며 동결 입력을 덮어쓰지 않는다. 새 실험은 새 폴더/실험ID와 사전 기준을 먼저 정한다. `approve_prompt_release.py`는 완전한 결과/usage/원본 해시를 확인한 뒤 서명해 비공개 명세를 등록하지만 자동 승격하지 않는다. `check_prompt_cache_eligibility.py`는 선택 완료 후 CountTokens만 사용한다.

프롬프트 제어는 공개 운영 검증을 완료했다. 실제 사용자 A/B와 개인 캐시는 미적용이다.
