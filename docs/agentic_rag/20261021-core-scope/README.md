# 핵심 수치 누락 감지·적용 범위 전달 — 100쌍 재검증, 운영 보류

**결론:** 구현과 별도 개발셋 보완, 새 전후100시도씩·Pro200답변 평가를 완료했다. 정답률89→95%, 충실도100→100%로 개선됐지만 근거 페이지 적중80→76%가 사전 비열등 기준을 통과하지 못했다. 기본OFF를 유지하며 이번 후보의 공개 배포·브라우저 기능 검증은 진행하지 않았다. ‘운영 개선 완료’로 주장하지 않는다.

## 문제와 변경

이전 실험에서 페이지는 적중했지만 필요한 수치가 청크에 없는데도 검색을 끝내고, 문서 population 메타데이터가 QA 문맥에 전달되지 않는 문제가 확인됐다. 이번 후보는 두 지점을 바꾼다.

1. controller-v6/recipe core-scope-v7는 필수 missing_core 배열로 질문의 핵심 수치·단위·분류명 등 누락을 명시한다. 배열이 비어 있지 않으면 sufficient=true가 함께 나와도 종료하지 않는다. 두 번째 검색 이후에도 누락이 남으면 근거를 노출하지 않고 보류한다.
2. _scoped_context가 출처별 population을 메타데이터·지시 아님으로 표시해 검색 평가와 최종 QA 문맥에 전달한다. 동일(source,population)은 중복 렌더링하지 않고 원래 메타데이터는 보존한다. 표시값은240자로 제한하고 잘리면 표시한다. 헤더·범위·본문 모두 같은6000자 안에 포함한다.

기존 점수 게이트, 최초 근거 보존, 최대8문서·2회 검색·2회 평가·기본35초·컨트롤러512출력토큰·공유 호출 예산을 유지한다. 잘린 구조화 출력은 거절한다. 새로운 DB 쓰기·자동 저장·유료 인프라 변경은 없다. 베이스 QA 프롬프트와 모델 선택은 유지한다.

## 별도 개발

[최초 개발](development/cases.json)은 가상의 수치·참조만 사용한12개 메커니즘 fixture다. 실제 영양 권고나 주 평가40문항의 답을 프롬프트에 넣지 않았다. 최초 실행에서 일부 문맥에 질문이 지칭한 가상 참조명이 빠진 오류와, ‘적용되지 않음’을 missing_core로 잘못 분류하는 문제를 찾았다.

참조명·띄어쓰기를 바로잡은 [development-v2](development-v2/cases.json)는 질문·골드를 유지한다. 임의의 다음 날 조정을 필수 항목으로 분류하는 문제도 남아, 실제 영양 수치 없는 일반적인 판단 예시를 추가했다. 수치가 없는 표준량 요청은 재검색하고, 정의+사용자 제안 보상 조정은 정의만 답하며 보상을 미확인으로 남기고, 범위가 제한된다는 근거는 ‘아니다’라는 답으로 인정한다.

[development-v3](development-v3/cases.json)는 수정된 같은12개를 전체 재실행했다. 후보 검색/보류 흐름12/12 일치, Pro 정답12/12·충실12/12; baseline Pro 정답7/12·충실12/12였다. [개발 품질 요약](development-quality-summary.json). 이는 합성 기능 검증이며100건 성능 증거와 구분한다. 각 실패 실행과 보완 전 소스는 그대로 보존한다.

## 동결 비교

주 비교는 동일 개발40문항을 반복한 조건별100시도, 총200시도다. 독립100질문/실제100사용자 결과가 아니다. 이전16363a06의 controller-v3/recipe-v4 코드와 자체 assessor/formatter를 baseline으로 고정하고, 후보를 새로 생성해 같은 Pro Batch A/B 루브릭으로 채점한다. 어느 쪽도 이전 답변을 재사용하지 않는다.

[protocol.json](protocol.json), [baseline](baseline-agentic-v4.py.txt), [후보 동결본](candidate-frozen.py.txt), [cases](cases.json). 실제 검색은 Dense k4/no-reranker로512MiB 경로를 재현하며 큰 호스트 Hybrid와 구분한다. 인증·DB·브라우저를 제외한 검색/생성 경계 실험이다. 사용자 기록 최신성은 이 실험의 측정 대상이 아니다.

정답률95%·최소2%p개선, 충실도/페이지근거/실패 비열등, 중앙값·p95각1.5배이내, 완전한 비용 계측과2배이내 비용을 요구한다. 추가로 HTTP 대체 응답이 완료돼도 loop timeout/controller_error/retrieval_error를100시도 분모에서 집계하고 증가 시 채택하지 않는다. 이 엄격한 operational gate는 본 실험 시작 전에 고정했다. 다른 프로젝트나 과거 실험의 미완료 비용을 소급해 완료로 바꾸지 않는다.

비용은 실제 제공자 토큰과 고정 API 단가 기반 추정치이며 임베딩을 포함한다. Pinecone·호스팅·세금·청구서와는 다르다. Pro 최종 평가 비용과 개발/최소 호출 비용은 분리한다. 생성 원본의 correct/faithful 초기값은 지연 채점용 placeholder이므로 최종 성적이 아니다. 최종 품질은 (attempt_id, condition)으로 Pro 평가 파일을 연결해 집계한다.

## 회복한 사례와 남은 원인

[짝 비교](paired-quality-changes.json)에서 정답 회복6건·정답 퇴행0건이다. 비만 진료 지침의 적용 범위를 빠뜨리던4건은4/4 회복했다. 에너지 상한섭취량 표 해석은0/4→2/4로 개선했지만 한국어2건의 불필요한 보류는 남았다. 모델이 표를 충분하다고 평가한 뒤 QA가 보류했으므로 컨트롤러 통과가 최종 답변 완성을 보장하지 않는다.

[실패·페이지 변화 원본 검토](candidate-error-review.json): 영어 류신 수치 질문3시도는 첫 청크에 필요한 수치가 없다는 점을 감지해 모두2회 검색했다. 그래도 필요한 수치를 확보하지 못해 round_limit에서 보류했다. 기존은 페이지가 적중해도 수치를 빠뜨린 채 종료했다. 이번 변경은 **조기 종료 감지와 허위 수치 방지는 개선했지만 정확한 청크 회수까지 해결하지 못했다.** 영어 류신 질문은3/3 미해결이며 같은 그룹의 한국어3시도는 정답이었다.

페이지 적중은 기존 대비5건 하락·1건 상승으로 순4건 감소했다. 하락5건 중3건은 위 보류로 최종 근거를 비운 경우, 나머지2건은 Pro가 답을 지지한다고 본 다른 페이지가 회수됐지만 사전 허용 페이지 목록에는 없는 경우다. 후자를 실험 뒤 정답 페이지로 추가해 게이트를 통과시키지 않았다. 페이지 적중과 답변의 핵심 사실 충족은 서로 다른 지표이며, 95% 정답만으로 채택하지 않았다.

다음 개선 후보는 별도 개발 문항에서 문서·페이지·인접 청크를 추적하는 제한된 재검색과 표 헤더/각주를 보존하는 문맥 구성이다. 먼저 영문 질의가 같은 페이지의 다른 청크만 반환하는 원인을 query·chunk ID 로그로 분리하고, 현재2회·8문서·6000자·호출 예산 안에서 설계해야 한다. 표의 빈 칸만으로 UL 부재를 추론하도록 강제하거나 본 평가의 류신 정답 수치를 프롬프트에 주입하지 않는다. 이후 새100쌍 검증이 필요하며 이번 성적을 소급 변경하지 않는다.

## 검증·운영 상태

- 백엔드 전체 회귀: **1518통과·기존 skip1·경고3**, exit0. 테스트를 삭제하거나 새로 건너뛰지 않았다. 경고는 기존 Pydantic/문서 로더 의존성의 사용 중단 안내다.
-200고유 시도와200평가의 키 일치, 조건별100건, 후보A/B 각50, 전 실험과 동일 cases 바이트, 동결 baseline/후보/벤치마크 해시를 확인했다.
- 기본 설정 `AGENTIC_RAG_ENABLED=false`를 유지했다. 변경은 연구/검증용 GitHub 기록으로 남기며 Render 자동 배포는 생략한다. 미통과 후보를 공개 배포하거나 공개 브라우저에서 활성화했다고 주장하지 않는다.
- [공개 API 읽기 전용 확인](public-health.json): `/health` 정상, 공개 commit은 `7dfbda0f14e556c7def56a16138597db68d123d5`로 유지된다. 이는 서비스 상태 확인이며 후보 기능의 브라우저 검증을 대신하지 않는다.
- 인증·사용자DB·기록 저장은 사용하지 않았다. 사용자 기록 최신성·브라우저 체감 지연·수시간 부하는 본 비교의 측정 범위 밖이다. Pro 자동 루브릭 평가이며 Ragas나 독립 사람 평가가 아니다.
