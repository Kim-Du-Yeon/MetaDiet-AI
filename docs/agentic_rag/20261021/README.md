# Agentic RAG 근거 보존 재검증 — 2026-10-21

## 결론: 구현·비교 완료, 운영 적용 보류

재검색 결과가 기존 근거를 통째로 대체하던 문제를 수정했다. 최초 검색의 점수 기준을 통과한 근거를 먼저 유지하고, 새 근거를 중복 제거해 추가한다. 최대 8문서·6,000자이며 평가와 최종 답변에 같은 한도를 적용한다. 저점수 문서를 승격하지 않고 실패 시 보류한다. 최대 검색 2회·컨트롤러 2회·기본 35초 및 공유 호출 예산은 유지했다. 컨트롤러 프롬프트 v1은 변경하지 않았다.

## Pro 한도와 기존 200건 평가 마무리

최소 호출 성공만으로 잔여 할당량을 보장할 수 없었다. 온라인 Pro 평가가 일일 한도 429로 다시 중단되어, 공식 문서의 별도 Batch 할당량을 사용했다. 이전 유효 평가 100건과 이번 온라인 4건은 그대로 유지했고, 미평가 답변 95건만 Batch로 평가했다. 원래 생성 실패 1건은 실패로 남겼다. 총 200시도의 상태가 모두 확정됐다.

| 기존 실험 | 단일 검색 | Agentic v1 |
|---|---:|---:|
| 시도 | 100 | 100 |
| 정답률(실패 포함) | 87% | 91% |
| 근거 충실도 | 99% | 100% |

기존 평가는 온라인 구조화 출력과 native Batch 인터페이스를 혼합했다. 모델·루브릭·출력 2048토큰·thinking low는 같지만 래퍼까지 동일하다는 뜻은 아니다. [완료 집계](historical-quality-summary.json), [200개 상태](historical-final-grades.jsonl).

## 근거 보존 전후 동일 사례 100시도씩

새 실험의 baseline은 단일 검색이 아니라 Agentic v1이고, candidate는 근거 보존 v2다. 같은 동결 개발 40문항을 반복한 조건별 100시도다. 질문·코퍼스·namespace·생성 모델·프롬프트·동시성 3을 고정하고 순서를 균형 배치했다. Dense 경로이며 큰 호스트의 Hybrid 비교가 아니다.

품질 평가는 양쪽 답변을 A/B로 가리고 각 답변의 실제 근거와 골드에 대해 독립 채점했다. A/B 배치는 50/50이다. 전체 100쌍을 동일 Pro Batch 방식으로 평가했으며, 사전 온라인 1쌍은 최종 품질 집계에서 제외했다. Batch 전환은 제출 전 protocol에 기록했다.

| 지표 | Agentic v1 | 근거 보존 v2 |
|---|---:|---:|
| 생성·최종 평가 완료 | 100/100 | 100/100 |
| 정답률 | 89% | 89% |
| 근거 충실도 | 100% | 100% |
| 근거 페이지 적중 | 74% | 75% |
| 실패·타임아웃 | 0/100 | 0/100 |
| 중앙값 | 14.739초 | 14.126초 |
| p95 | 22.983초 | 21.720초 |
| 확인 가능한 생성·컨트롤러 비용/100건 | $0.557182 | $0.547847 |
| 최종 Batch 평가 비용(쌍별 반분)/100건 | $0.273784 | $0.273784 |

임베딩 SDK의 실제 사용 토큰 메타데이터가 없어 전체 비용은 미완성이다. UTF-8 바이트 기반 보수적 프록시는 청구 비용이 아니다. Batch 평가 비용은 서비스 응답 비용과 구분한다. [원본 시도](attempts.jsonl), [평가](batch-pairs-job.grades.jsonl), [집계·게이트](summary.json), [고정 조건](protocol.json).

## 실패 원인·해결 범위·남은 작업

단위 테스트로 기존 좋은 근거가 재검색 후 유지되고 저점수 신규 근거가 이를 대체하지 않는 것을 확인했다. 그러나 이 구조적 수정만으로 정답률이 오르지는 않았다. candidate 오답 11건의 평가 사유는 답변 가능한 문항의 보류 8건과 대상 집단·계산식 출처 같은 필수 조건 누락 3건이다. 근거 충실도 100%는 골드 질문의 완전한 정답을 보장하지 않는다. 특히 표의 함의를 읽지 못한 보류가 남았다. 고정셋을 보고 문항별 예외를 추가하지 않았다.

사전 기준 정답률 95%·최소 2%p 개선에 미달했고 전체 비용도 미확정이므로 rollout_gate=false다. 기본 AGENTIC_RAG_ENABLED=false를 유지하고 후보를 운영 배포하지 않는다. 따라서 후보의 공개 브라우저 검증은 수행하지 않았으며 완료로 표시하지 않는다. 다음 단계는 별도 개발셋에서 표 근거 해석·불필요 보류·필수 조건 누락을 개선한 뒤 독립셋과 임베딩 실제 비용을 포함해 재평가하는 것이다.

## 공식 문서와 재현

[Gemini rate limits](https://ai.google.dev/gemini-api/docs/rate-limits): 프로젝트 단위 한도와 태평양 자정 RPD 초기화, Batch 별도 할당량.
[Batch API](https://ai.google.dev/gemini-api/docs/batch-api): 비동기 평가·표준 대비 50% 가격·목표 24시간·생성 요청 비멱등성. 제출 의도를 배타적 파일 생성으로 먼저 기록하고 결과 조회만 재시도한다.
[LangGraph Agentic RAG](https://docs.langchain.com/oss/python/langgraph/agentic-rag): 검색 평가·재작성·재검색 패턴. 기존 근거 보존은 이 프로젝트의 추가 안전장치다.

`batch_agentic_judges.py collect --job docs/agentic_rag/20261021/batch-pairs-job.json`으로 기존 작업을 조회한다. 새 제출은 별도 job 파일을 사용하며 기존 job을 삭제해 재제출하지 않는다. `analyze_agentic_rag.py docs/agentic_rag/20261021 --grades-name batch-pairs-job.grades.jsonl`로 집계를 재현한다. 실제 실행은 backend/venv 인터프리터를 사용한다.
